# Deployment

This platform is deployed as a **brand-new service**, independent of the old
production deployment (the old service identities are inventoried and
delisted in `ISOLATION-AUDIT.md`). Nothing in this repo points at, proxies
to, or reuses the old deployment. You create a *new* service and fill in
*new* values.

## Target: Render (recommended)

`render.yaml` defines a single web service. It is intentionally minimal and
contains **no live secrets** — secrets are generated or set in the dashboard.

### Steps

1. **Create the new database** (see `DATABASE.md`) and note its connection
   string.
2. In Render, create a **new** Web Service from this repo (do *not* open or
   modify the old service). Enable **Blueprints** so `render.yaml` is read —
   that creates the 1 GB persistent disk (`bello-data` at `/var/data`) and all
   environment variables declared in the file. The Blueprint uses only Render
   supported fields and pins Node through `NODE_VERSION` / `.node-version`;
   a malformed Blueprint is not an acceptable substitute for the disk being
   present. **Do not skip this step**: without a volume, every SQLite-backed
   madrasa you add is deleted at the next deploy. See
   [`PERSISTENCE.md`](PERSISTENCE.md).
3. When prompted, provide the values marked `sync: false` in `render.yaml`:
   - `DATABASE_URL` — the NEW connection string
   - `SUPER_ADMIN_PASSWORD` — a strong, new password
   - `PUBLIC_URL` — the new service URL Render assigns
4. `SESSION_SECRET` is auto-generated by Render (`generateValue: true`).
5. Deploy. On first boot the service logs the database file it opened (and any
   other `*.sqlite` in that directory, which it will not read), runs migrations (a `pre-migration`
   snapshot is written first), creates the fresh schema, seeds the single
   super-admin from `SUPER_ADMIN_USERNAME` / `SUPER_ADMIN_PASSWORD`, and logs a
   storage verdict — `ok: database, uploads and backups are on a persistent
   volume (mounted volume …)` is what you want to see.
6. Open `Platform → Backups & storage` once and confirm the banner is green.
   A snapshot is taken every 6 hours (`BACKUP_INTERVAL_MINUTES`) and on every
   graceful shutdown; *Download* takes one off-platform.

### render.yaml env vars (what each does)

| Key | Source | Notes |
| --- | ------ | ----- |
| `NODE_VERSION` | fixed `22.22.3` | supported Render setting; also pinned in `.node-version` |
| `NODE_ENV` | fixed `production` | enables production validation |
| `DATABASE_DRIVER` | fixed `mysql` | use the new MySQL DB; never let production silently fall back to SQLite |
| `DATABASE_URL` | you set (`sync: false`) | NEW DB only |
| `SESSION_SECRET` | Render-generated | 32+ chars, required in prod |
| `SUPER_ADMIN_USERNAME` | fixed `admin` | change after first login |
| `SUPER_ADMIN_PASSWORD` | you set (`sync: false`) | strong, new |
| `PUBLIC_URL` | you set / Render-assigned | new domain |
| `LOGIN_RATE_LIMIT` / `API_RATE_LIMIT` | sensible defaults | |
| `DATA_DIR` | fixed `/var/data` | everything the app writes lives here |
| `UPLOAD_DIR` / `BACKUP_DIR` | fixed `/var/data/…` | logos/photos + JSON snapshots, on the disk |
| `PERSISTENT_VOLUME_DIR` | fixed `/var/data` | what the storage probe compares against |
| `BACKUP_INTERVAL_MINUTES` / `BACKUP_KEEP` | `360` / `10` | automatic snapshots and retention |
| `PUBLIC_RATE_LIMIT` / `PUBLIC_APPLY_LIMIT` / `PUBLIC_VERIFY_LIMIT` | `600` / `8` / `12` | limits for the logged-out public site |
| `DATA_PERSISTENT_ACK` | unset | set to `1` only when the disk is yours and survives reboots |
| `AUTO_RESTORE_ON_EMPTY_DB` | unset (on) | a boot that finds an EMPTY database restores the newest snapshot; `0` disables |

### Repairing or verifying an existing Render service

A committed `render.yaml` changes a service only when that service is managed
and synced as a Render **Blueprint**. If the live service was originally
created by hand, check its Dashboard configuration before deploying this
release — do not assume the file has already attached a disk to it:

1. **Disk:** the service must show a persistent disk mounted at `/var/data`
   (named `bello-data` in this Blueprint, at least 1 GB). If it does not, add
   one from the service's **Disks** page in the Render Dashboard, with mount
   path `/var/data`. Render redeploys after you save. A disk means one instance,
   and each deploy has a short outage, because Render stops the old instance
   before it starts the new one.
2. **Database environment:** `DATABASE_DRIVER` must be `mysql` and
   `DATABASE_URL` must be set to the intended database. Render masks the URL;
   confirm it is present, never paste it into source or logs. This Blueprint
   does not set `DB_SSL`, so the connection is not encrypted; see
   [DATABASE.md → TLS](DATABASE.md#tls-encrypting-the-mysql-connection) before
   you turn it on.
3. **Filesystem environment:** `DATA_DIR=/var/data`,
   `UPLOAD_DIR=/var/data/uploads`, `BACKUP_DIR=/var/data/backups`, and
   `PERSISTENT_VOLUME_DIR=/var/data` must all be set exactly as shown. If
   `DATA_DIR` is missing but the disk is mounted, the app still uses `/var/data`
   on Render, so uploads and backups stay on the disk. The first boot line
   shows the directory that was chosen.
4. Redeploy and read the first boot lines. The target is `driver: mysql` and a
   `Storage: ok` line with `data=/var/data`. There must be no
   `EPHEMERAL_DATA_DIR`, `EPHEMERAL_UPLOADS`, or `EPHEMERAL_BACKUPS` warning.
   An `Ignoring invalid configuration option` line from mysql2 must not appear.

For safety, this release **refuses to boot on Render in production** when
SQLite resolves to a filesystem that is not actually a persistent mount. That
fails the deploy before migrations or seeds can create an empty database,
rather than allowing a service that will lose its institutions on the next
restart. Do not set `DATA_PERSISTENT_ACK=1` just to hide this failure; attach
the disk or configure MySQL with `DATABASE_URL` instead.

### Resetting the super-admin password

`SUPER_ADMIN_PASSWORD` is only read **when the super-admin account is first
created** (first boot of a fresh database, or `npm run seed`). Changing the
env var afterwards — e.g. in Render → Environment — does **not** update the
password already stored in the database, and seeding intentionally skips an
existing super admin so a password the admin later changed in the app is
never silently overwritten. That is the most common cause of
"Invalid username or password" after "I already set the password in Render".

The command prints the database it is about to touch and **refuses to run** if
that SQLite file does not exist yet — creating an empty database beside your
real one is how tenants start looking deleted. (`--force` overrides, for a
genuinely new install.) The database file has exactly one name per `DATA_DIR`
(`madrasa_platform.sqlite`) and no longer changes with `NODE_ENV`, so a shell
run and the service agree on which file they mean; see
[`PERSISTENCE.md`](PERSISTENCE.md) §1.1.

To make the account match the value currently in the environment, run the
explicit reset command against that database:

- **Render:** open the service's **Shell** (or `render shell <service>`) and
  run `npm run reset-admin-password`
- **Anywhere:** `npm run reset-admin-password` with the env vars of the
  target environment

The command sets the super admin's password to the current
`SUPER_ADMIN_PASSWORD` value (and creates the account if it does not exist
yet). No restart is required — just log in again.

**Usernames are case-insensitive.** Sign-in lower-cases whatever is typed, so
the stored username is lower-cased too (`SUPER_ADMIN_USERNAME=Admin` and
`admin` are the same account). Earlier releases stored the variable verbatim,
which could create an account that no input would ever match; boot and
`npm run reset-admin-password` now repair such a row automatically.

### "Nothing happens when I sign in"

A platform whose database has **no accounts at all** used to answer
`Invalid username or password` — indistinguishable from a typo, and the
reason the documented `admin` login appeared to do nothing. Two guards now
make that state impossible to reach silently:

- **Boot:** a production boot with no super admin and no `SUPER_ADMIN_PASSWORD`
  **fails** with an explicit error instead of starting a platform nobody can
  enter. (In development the seed generates a password and prints it.)
- **Login:** if the users table is empty, `POST /api/auth/login` answers
  `503 NO_ACCOUNTS` and the form displays *"This platform has no accounts yet…"*
  with the command to run. This cannot leak account information — it only
  fires when there are no accounts to enumerate.

You can check the account exists in your database with:

```sql
SELECT id, username, role FROM users WHERE role = 'super_admin';
```

## Production validation (fail-fast)

`server/config.js` refuses to boot in production if any of these are wrong,
so a misconfigured deploy can never silently reuse another database:

- `SESSION_SECRET` ≥ 32 chars and not the template value
- `SUPER_ADMIN_PASSWORD` not the template value
- MySQL configured via `DATABASE_URL` or the four `DB_*` vars

## Persistent disk, uploads and backups (do not skip)

| Question | Answer |
| -------- | ------ |
| Where is the dev database? | `DATA_DIR` (default `./data`), SQLite |
| Where do uploads go? | `UPLOAD_DIR` (default `DATA_DIR/uploads`) |
| Where are backups? | `BACKUP_DIR` (default `DATA_DIR/backups`), plain JSON |
| What survives a redeploy without a volume? | **Nothing.** That is the "my madrasa disappeared" bug |
| How do I check a running host? | `GET /api/platform/backups/diagnostics`, or `Platform → Backups & storage` |
| How do I restore? | that page, or `npm run backup -- --restore <file>` (works while the app is down) |

`render.yaml` already mounts `bello-data` at `/var/data` and points all three
directories at it. Docker, Fly and VPS equivalents are in
[`PERSISTENCE.md`](PERSISTENCE.md), including the warning codes
(`EPHEMERAL_DATA_DIR`, `DATA_LOSS_DETECTED`, …) and what each one means.

## Public site (viewable before login)

The landing page, the madrasa directory, each school's public profile, the
result checker and the online admission form are served to anonymous visitors.
Nothing requires a session, and nothing is exposed that a madrasa has not
switched on itself:

- `madaris.public_listing` — appear in the directory (default **on**)
- `madaris.public_results` — allow result checking; only *published* term
  summaries are ever returned, and each printed card uses a 15-minute token
- `madaris.public_admissions` — accept online applications (the school reviews
  them in `Admissions`, and approving one creates the pupil's record)
- announcements need `publish_public` (optionally `publish_until`)
- `public_directory_enabled` in `Platform → Settings` is a platform-wide kill
  switch; `public_site_title` / `_tagline` / `_intro` and `public_contact_*`
  brand the landing page

Writes are rate limited per IP (`PUBLIC_APPLY_LIMIT`, default 8/hour), a
honeypot field and a 24-hour duplicate guard keep bots out of the queue, and
every public result lookup is written to the activity log
(`public.result_view` / `public.result_failed`).

## Other hosts

The app is a standard Node/Express server and runs on any Node ≥ 22 host
(Railway, Fly, a VPS, etc.). The contract is: set the same env vars from
`.env.example` (new values only) and run `npm start`. There is no
host-specific config baked in.

## Performance and multi-instance operation

**Sessions live in the database** (`app_sessions`), not in process memory.
Any instance can serve any request, so a load balancer may round-robin
between instances without sticky sessions — verified by load test: two
instances sharing one SQLite database, 2 000 concurrent users with traffic
alternating per request, zero authentication failures, and materially lower
p50/p90 latency than a single instance at the same throughput. The only
things that must match across instances are `SESSION_SECRET` and the
database.

Operation knobs (all optional):

| Variable | Default | Meaning |
| --- | --- | --- |
| `LISTEN_BACKLOG` | 1024 | TCP accept-queue depth. Node's own default is 511, which drops SYNs during a connection burst (a deploy, a whole school logging in at 08:00). Raise it before load spikes. |
| `PERF_MONITOR` | off | `1` exposes the super-admin-only `/api/perf` endpoint: event-loop lag percentiles, heap, CPU, MySQL pool stats. Collects nothing unless enabled — use it for staging and load tests. |
| `SESSION_PRUNE_MINUTES` | 60 | How often expired session rows are deleted. Sessions are the one table that grows on every login; `0` disables the timer. |

Two per-process caveats when scaling out:

- **Rate limits are per process** (login attempts, API and public limits).
  With N instances behind one balancer an attacker gets N× the budget — set
  the limits accordingly if that matters on your host.
- **Scheduled backups run in every process** if `BACKUP_INTERVAL_MINUTES > 0`.
  Snapshots have millisecond-precise names and never overwrite each other, but
  you may prefer to set the interval on one instance only.

## What is NOT done here

- No real payment gateway is connected.
- No automatic migration of old data is performed (by design — the old data
  stays in the old system; migrate only if/when explicitly requested).
